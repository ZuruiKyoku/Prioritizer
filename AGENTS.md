## Project continuity

- At session start, locate the actual project/repository root and read `PROJECT_STATE.md` before planning or editing. Also read the applicable instructions in this file and any deeper agent files.
- If `PROJECT_STATE.md` is absent, inspect existing source, documentation, Git state and available project history, then create it. Absence does not prove this is a new project. Mark unknowns instead of inventing history.
- Treat it as the maintained handoff, checked against current source, Git and explicit user decisions. Distinguish implemented code, runtime-verified behavior, historical reports, plans, and unknowns. Record branch/commit/date and relevant evidence. Local-only work is not pushed work.
- After meaningful changes, decisions, tests, discoveries or blockers, update it in the same session. Before handoff, record what changed, verification actually performed, remaining issues, next steps and any uncommitted/unpushed work. Keep durable decisions; remove superseded status rather than appending contradictory claims.
- Keep these sections: End goal; Architecture; Decisions and workflow; Current status; Completed work; Known issues and gaps; Roadmap; Next steps; Verification and evidence; Session handoff.
- Preserve existing branch, test, acceptance and merge rules. This continuity policy grants no permission to merge, deploy, push unrelated work, or alter user data. Commit/push only within the user's authorized scope. Include the state update with the relevant code change when authorized.
- Do not store credentials, personal/customer data, raw chat transcripts or generated media in this file. Record minimal project facts and source pointers. State inaccessible or incomplete history explicitly; never claim universal chat access or automatic synchronization.
